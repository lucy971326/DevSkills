# 双源验证

通过干净上下文重新调查原始问题。目标是显著提高工程结论的可信度，而不是承诺绝对真相。

优先在两类高价值任务中使用：

- **源码验证**：一个 Agent 沿调用链追踪，另一个从实现点、状态写入点或测试反向核查；用原始代码验证主 Agent 的猜想。
- **架构设计**：Agent A 根据原始约束设计方案；Agent B 在看不到 A 方案的情况下，独立梳理约束、失败路径、复杂度陷阱、维护成本和最小替代方案。主 Agent 用 B 的现实检查结果审视 A，防止产出只在模型叙事中成立的“假好架构”。

## 工作流

### 1. 定义原子问题

把任务收敛为两个 Agent 都能明确回答的同一个问题。只提供原始问题、必要事实、源码位置和约束。

不得向子 Agent 传递主 Agent 的分析、猜测、候选结论或推理过程。使用中性描述，避免用“验证是否由 X 导致”植入预判。

### 2. 并行独立调查

在同一轮同时派出 Agent A 和 Agent B，并确保：

- 两者使用独立上下文，互相看不到结果。
- 两者回答同一个问题，但采用不同证据路径。
- Prompt 自包含、中性，不引用另一方或主 Agent 的判断。
- 优先检查原始材料，如源码、日志、官方文档和原始数据。
- 架构任务必须共享相同的真实约束，但不得向 A、B 泄漏主 Agent 的候选方案或偏好；B 也不得看到 A 的方案。

可采用自顶向下与自底向上、源码与官方文档、调用方与实现方等互补路径。

要求两者按相同结构返回：

```text
结论：
证据：
不确定点：
可能推翻该结论的情况：
```

### 3. 交叉审核

等待两者完成后，由主 Agent 比较结论及其证据路径：

| 情况 | 处理方式 |
|---|---|
| 结论一致，证据路径独立 | 作为高置信度结论采信 |
| 结论一致，但依据相同 | 视为单一证据源，降低置信度 |
| 细节不同 | 提取最小争议点并继续核实 |
| 结论矛盾 | 不立即站队，启动第三个干净上下文裁决 |
| 原始材料不足 | 明确报告未知，不强行统一结论 |

第三个 Agent 只接收中性的争议问题和必要原始材料，不得看到主 Agent 的预判或 A、B 的完整结论。

### 4. 报告结果

简洁说明：

- 哪些结论经过独立双源验证。
- 使用了哪些不同证据路径。
- 存在哪些分歧、不确定性或证据缺口。
- 最终结论及其置信度。

## 边界

简单文件查找、明确答案或低风险操作无需双源验证。紧急修复可以先实施最小改动，但交付前补充验证；涉及生产、数据或安全时不得跳过验证。
